CNCM: Compact Causal-Hybrid Next-Concept Modeling for edge-scale generation

I re-engineered Next-Concept Modeling (NCM) into a pure-PyTorch architecture that fits on a phone: zero codebook tables, causal prefix KV caching, recursive layer looping, and plan-guided fill-in-the-middle. Everything below is what I actually measured — including what didn't work.

Why I built this

NCM (Next-Concept Modeling) is a good idea that hits a wall on edge hardware. I read the reference implementation and kept running into the same three problems:

  • Codebook tables. Twelve separate FP32+EMA VQ tables (~151 MB for 12×4096×384) before you add a single backbone weight. On a 4 GB phone that's dead on arrival.
  • Non-causal windows. NCM uses bidirectional prefixes with 5×–11× sequence blowup. No incremental KV caching across chunks — useless for chat.
  • Discrete fragility. Even at 99.9% reconstruction, one wrong discrete code corrupts strict JSON tool-call syntax or a code identifier.
"I wanted something that actually runs on low-end Android and consumer iGPU laptops, not something that works on an A100 and hopes for the best."

So I rebuilt it from scratch in pure PyTorch (no CUDA-only kernels, no Triton). CNCM replaces VQ+EMA with implicit FSQ grids, makes prefixes strictly causal with KV caching, and adds a grammar-constrained Exact-AR mode so tool calls and code stay syntactically valid.

Architecture

CNCM has two stages. Stage 1 is a frozen concept tokenizer; Stage 2 is a shared dual-mode backbone.

Stage 1 · MultiscaleRFSQ

Embeds tokens into z₀ = GroupNorm(affine=False)(E(x)), then computes detached residuals rₖ = z₀ − sg(ẑₜ₋ₖ) across 8 convex scales ℓ = (1, 2, 4, 8, 12, 20, 36, 64). Each level projects to 4 bounded scalar coordinates on an 8⁴ grid:

c̃ⱼ = (Lⱼ−1)/2 + (Lⱼ/2)(1−ε)·tanh(hⱼ)

Result: implicit 4096-code space, no VQ table, no EMA buffers, < 5e-7 gradient-accumulation invariance.

Stage 2 · Dual-mode backbone

Causal prefix KV cache feeds a shared CNCMBlock stack (Pre-RMSNorm + QK-RMSNorm + GQA + SwiGLU). Two heads branch off:

  • Concept Mode — FactorizedConceptHead models 4096-way joint digit correlation in 71K params; ~23–32× fewer output MACs.
  • Exact-AR Mode — weight-tied head; JSONSchemaConstrainedMasker guarantees 100% JSON-schema syntax validity.
Recursive layer looping (CNCMBlock)

Weight-shared recursive looping trades FLOPs for parameter depth. On nano this gives 21–24 effective passes in 14.5M total parameters (12.29 MB packed INT4).

Negative result (Ablation A2): at 300 steps and equal parameters, non-looped 7×1 converges faster than weight-shared 7×3 (Concept loss 4.51 vs 5.95). Looping only pays off with more compute.

PG-FIM · Plan-Guided Fill-in-the-Middle

Cursor-aware infilling: a short Exact-AR plan <mlen_k> <kw> kw1 | kw2 </kw> guides parallel Concept Mode middle generation. Phase A repairs spans in Exact-AR; optional Phase B uses CopyAwareKeywordCrossAttention pointer decoding.

Results

Measured on NVIDIA A10/A10G, leakage-free held-out splits. I'm listing the disappointments first because they matter more than the wins.

What didn't work

  • Recursive looping (Ablation A2): non-looped 7×1 beats 7×3 at equal parameters and 300 steps. Looping needs more compute to justify itself.
  • Self-speculative verification: mathematically exact (greedy match = True) but 0.0 draft acceptance at short-training scale — runs at 0.239× vs plain AR. Not an accelerator yet.
  • Stage 3 GRPO/CISPO: runs stably but yields final_mean_reward = 0.0 — sparse rollout groups, zero variance.
  • Model-only PG-FIM at v1: 0.0% parse/compile/test. The earlier "100% compile" number was an artifact of opt-in template fallback, now disabled by default.
